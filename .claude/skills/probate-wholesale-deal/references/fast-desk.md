# Fast desk: time-sensitive work between the daily runs

The main runner (session `session_01VKtpFDZbbd6DhTxHVpZuwn`) does the heavy work three times a day: sourcing, deep-dives, expansion, reports. The fast desk (session `session_01VKtpFAuYZcMNrX5sQ8wvgc`, on its own schedule) runs every 2 hours during business hours and does only what shouldn't wait for the next main run. It can act as **any** worker: for each item it reads that worker's role file (`agents/<worker>.md`) and works as that worker, so workers added later are covered with no change here.

Hard limits from `references/daily-run.md` → "Hard limits" apply exactly as in a main run. Nothing goes out without the Compliance Officer's gate, and outreach follows `autonomy` and each market's `attorney_approved`. Only `active` workers act for real (`pipeline/workers.csv`): an item for a worker in `trial` or `probation` stays open for the main run, where it runs in shadow mode (`references/worker-lifecycle.md`). Workers decide within their written limits and log each decision in `pipeline/decisions-log.csv`; never act for `owner`.

## Each firing, in this order
0. **Don't collide with the main run.** Read the main runner with `get_session` (`session_01VKtpFDZbbd6DhTxHVpZuwn`). If its status is working or running, end now with "Main run in progress; skipped." Otherwise `git checkout main && git pull --rebase origin main`.
1. **Is there anything to do?** Count: open or escalated items on the board (`python3 scripts/handoffs.py sweep`, then `check`); new owner decisions (step 3); new replies if the inbox channel works (`channels.inbox_connected: true`). If all are zero, end now with "Nothing waiting." and commit nothing. Most firings should end here and cost almost nothing.
2. **Clear the handoff board.** Take open items oldest-first, with urgent and blockers ahead of the rest, at most 15 per firing. For each one, read `agents/<to_worker>.md` and the lead's files, then do what that worker would do: answer with evidence, or reassign it with a reason. A **normal**-priority request the size of a full deep-dive or a new market stays open for the main run. Among urgent items, take them in **critical-path order** (what the first closed deal waits on), not oldest-first: 1) attorney sourcing and engagement (`professional-network`, `legal-advisor`), 2) lead sources for live markets (`source-mapper`), 3) buyers (`buyer-list`), 4) documents (`legal-counsel`), then the rest; and give each urgent item a fair share of the time (about 10 minutes) before moving to the next, so every critical item moves every run. An **urgent** one doesn't wait for size (owner decision 2026-11-26): start it as its worker, do as much as your time allows (most valuable part first: e.g. the first market, the best-scored buyers), save the work, and `answer` nothing until it's complete; instead add a one-line progress note to the item's lead files or the worker's output file (`<date>: done X of Y, next: Z`) so the next run (fast desk or main) continues exactly where you stopped. Every run starts on a fresh, empty machine: anything only in `/tmp` is gone next run. Save what the next run needs (the exact source URL or path, the query, and the extracted rows you used, never a whole bulk file and never personal data beyond what the pipeline files already hold) in the repo with your progress note. Close answers to questions a worker asked once the answer is enough. Never act for `owner`.
3. **Owner decisions.** `db_whoami`, then for `outreach`, `sign` and `wire`: `db_list` `data/users/<id>/decisions/<queue>` on the dashboard, save each output, and run `python3 scripts/owner_decisions.py import <queue> <file>`. Act on every row with an empty `applied`, exactly as runbook step 1 describes (approved: compliance gate, then send if a channel works, or mark it print-ready; changes: redraft; rejected: Dead with the note; sign/wire done: record it). Set `applied` when done.
4. **Replies** (only when the inbox channel works). Collect new received emails (Resend), log them in `pipeline/inbox-log.csv`, and route each as `agents/communications.md` and `agents/reply-desk.md` say. A stop request goes on the stop list at once. Draft an answer into `leads/<id>/outreach-drafts.md`. A counter-offer becomes a handoff to `negotiator` (urgent). Send only what the autonomy rules allow (market's `attorney_approved`, tested channel, Compliance PASS, 90-day wait) and log it in `pipeline/outbound-log.csv`; everything else waits as a held draft.
5. **Save.** Run `python3 scripts/handoffs.py check`. Commit only the files this firing changed (`Fast desk YYYY-MM-DD HH:MM: N handoffs, M decisions, K replies`), then `git pull --rebase origin main` and push, retrying up to 3 times. On a rebase conflict in a file you didn't change, keep the other side. In one you did change, re-apply your small edit on top of the latest version.
6. **Dashboard: don't publish.** The dashboard service asks for approval on every upload and data write, and an unanswered prompt would stall every later firing. The page already shows the owner's decisions the moment they're made. Handoffs, replies and decisions handled here appear at the main runner's next refresh.
7. **End** with one short line: handoffs cleared, decisions applied, replies handled, anything escalated to the owner.

## What the fast desk never does
Sourcing, deep-dives of new leads, market expansion, legal refresh, the daily report, or the weekly calibration: those stay with the main runner. It never edits `config.yaml`, the role files or the runbook (learning goes through the main run's step 7b). It also never starts a second firing while one is running.
